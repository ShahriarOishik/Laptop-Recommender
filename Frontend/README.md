# Laptop Recommender System Frontend

A React single-page application for discovering, filtering, comparing, shortlisting, and requesting laptop recommendations. It is the UI for the RAG (Retrieval-Augmented Generation) backend in this same repository (`../Backend`), and also includes a local mock recommender for offline demos or frontend-only development.

> **Note:** this directory is the frontend half of the monorepo. The real LLM/embedding/FAISS/Qdrant/Spark pipeline lives in `../Backend` and is implemented there, not here. By default this app talks to that real backend; the mock recommender is an opt-in offline fallback (`VITE_USE_MOCK_API=true`), not the default experience.

## Features

- Conversational laptop recommendations with suggested prompts and refinement chips.
- Requirement filters for price, RAM, storage, CPU, GPU, brand, use case, display size, and operating system.
- Recommendation cards with match scores, requirement status, reasoning, and evidence panels.
- Laptop exploration with search, sorting, filters, details, compare, and shortlist actions.
- Side-by-side comparison of up to four laptops.
- Saved laptop shortlist.
- Light and dark themes.
- Persisted chat sessions with a developer page that exposes returned RAG/debug metadata.
- A local mock data set and recommender, available as an opt-in offline fallback for demos or frontend-only development without the backend running.

## How Recommendations Work

### Default: real backend

With `VITE_USE_MOCK_API=false` (the default), the app streams requests to `${VITE_API_BASE_URL}/chat/stream` via Server-Sent Events. The backend (`../Backend`, a FastAPI service) parses the query and filters, embeds and retrieves over a FAISS/Qdrant index of laptop specs and reviews, and generates a grounded answer through a Groq/Gemini/OpenRouter LLM fallback chain — see [Backend API contract](#backend-api-contract) for the exact request/response shapes.

### Optional: local mock recommender (offline demo)

Set `VITE_USE_MOCK_API=true` to run without a backend at all. In this mode the browser makes no network calls; it runs the logic in `src/mocks/mockEngine.ts` against 18 hard-coded laptop records from `src/mocks/laptops.ts`.

The mock recommender:

1. Parses a small set of query patterns and keywords. It recognizes budgets such as `under 1000`, RAM such as `16 GB RAM`, storage such as `512 GB SSD`, and keywords for use cases, NVIDIA/RTX, portability, battery, gaming, coding, and machine learning.
2. Combines parsed requirements with the filters selected in the chat UI.
3. Scores each mock laptop using fixed weights: budget 28%, RAM 18%, storage 10%, GPU 20%, use-case overlap 14%, portability 5%, and battery 5%.
4. Ranks the laptops and returns the best matches with template-generated reasoning, requirement labels, mock evidence, and simulated latency values.
5. Displays up to the requested top results. The chat interface requests three results.

The mock evidence is built from laptop specifications and canned category-based review text. It is not retrieved from a database or generated by a language model. The mock debug payload contains placeholder strings for UI demonstration only; they do not reflect anything about the real backend's model or index.

## Application Routes

| Route | Purpose |
| --- | --- |
| `/` | Chat-based recommendations, filters, evidence, follow-up prompts, and chat sessions. |
| `/explore` | Browse laptops, search by name or brand, sort, filter, compare, save, and open details. |
| `/laptop/:id` | Laptop specifications, similar laptops, retrieved-review presentation, and recommendation tags. |
| `/compare` | Compare two to four selected laptops in a table. |
| `/shortlist` | View and manage saved laptops. |
| `/developer` | Inspect debug/RAG details associated with the latest completed chat response. |

`Ask AI to Compare` on the comparison page adds a message and navigates to the chat page. It does not automatically submit a recommendation request.

## Run Locally

### Prerequisites

- Node.js 20 or newer is recommended.
- npm.
- The backend running (see `../Backend/README.md`) if you want real recommendations instead of the offline mock.

### Installation

From the repository root:

```bash
cd Frontend
npm install
```

Create a local environment file from the example:

```bash
cp .env.example .env.local
```

Start the development server:

```bash
npm run dev
```

Vite prints the local URL, normally `http://localhost:5173`.

## Environment Configuration

`.env.example`:

```env
VITE_API_BASE_URL=http://localhost:7860
VITE_USE_MOCK_API=false
```

| Variable | Purpose |
| --- | --- |
| `VITE_API_BASE_URL` | Base URL of the running backend (default assumes it's on port 7860, matching `../Backend`'s default). Unused in mock mode. |
| `VITE_USE_MOCK_API` | Set to exactly `true` to use the local offline mock instead of the real backend. Anything else (including unset) uses the real backend. |

Restart Vite after changing environment variables. When the frontend and API use different origins, configure CORS on the backend (`../Backend`'s `CORS_ORIGINS` setting). This frontend does not configure a development proxy, authentication, credentials, or request timeout.

## Backend API Contract

This mirrors `Backend/app/models.py` and the real routes in `Backend/app/main.py` field-for-field (snake_case). The full DTO types are in `src/types/api.ts`.

### Health check

```http
GET /health
```

Returns `{ status, version, embedding_model, embedding_ready, faiss_ready, metadata_backend, metadata_ready, qdrant_ready, llm_providers, errors }`. The frontend uses `embedding_model` for the developer page's debug display.

### Chat (streaming)

```http
POST /chat/stream
Content-Type: application/json
```

Request body:

```json
{
  "message": "I need a lightweight laptop for programming under 1000, prefer Intel CPU.",
  "conversation_id": "optional-existing-conversation-id",
  "filters": {
    "min_price_usd": null,
    "max_price_usd": 1000,
    "min_ram_gb": 16,
    "min_storage_gb": null,
    "brands": [],
    "operating_systems": []
  },
  "top_k": 3,
  "force_retrieval": false
}
```

Note: the backend has no dedicated filter for use case, CPU brand, or display size — the frontend folds those into the free-text `message` instead (see `augmentMessage` in `src/services/recommendationService.ts`) so the backend's own query parser picks up the intent.

Response is Server-Sent Events, in order:

- `event: recommendations` — fires as soon as retrieval finishes, before the LLM answer: `{ recommendations, status, outlier, message, matched_count, intent }`.
- `event: answer` — `{ answer, provider }` (`provider` is `"groq"`, `"gemini"`, `"openrouter"`, or `"retrieval_only"`).
- `event: card_insights` — `{ card_insights: { [laptop_id]: { match_reason, strengths, tradeoffs } } }`.
- `event: done` — the full, authoritative response (all fields above, plus `parsed_query`, `retrieval_latency_ms`, `cache_hit`, `conversation_id`, `referenced_laptop_ids`). This is always what the UI ultimately renders from.
- `event: error` — `{ detail }`.

Each `recommendation` item: `{ laptop_id, brand, model, price_usd, score, semantic_score, filter_aware_score, constraint_fit_score, soft_preference_score, value_score, price_fit_score, spec_score, metadata, sources }`, where `metadata` is the laptop's full spec record (`cpu_full`, `gpu_full`, `ram_capacity_gb`, `storage_capacity_gb`, `weight_kg`, `os_normalized`, `gpu_tags`, `price_usd`, ...) and `sources` is a list of the retrieved chunks grounding this recommendation (`{ vector_id, chunk_id, laptop_id, chunk_type, score, text }`).

### List laptops

```http
GET /laptops?search={search}&sort=...&min_price_usd=&max_price_usd=&min_ram_gb=&min_storage_gb=&brands=&operating_systems=&limit=60&offset=0
```

Returns `{ total, limit, offset, items, facets: { brands, gpu_tags, operating_systems } }`.

### Get laptop details

```http
GET /laptops/:id
```

Returns `{ laptop_id, laptop, chunks }`, where `laptop` includes `content_by_type` (the laptop's own text grouped by chunk type) and `chunks` is the raw retrieved chunk records for that laptop.

### Get similar laptops

```http
GET /laptops/:id/similar?limit=3
```

Returns `{ laptop_id, similar: [...] }`, each entry including a `similarity` score.

## State And Persistence

| Data | Storage |
| --- | --- |
| Theme preference | `localStorage` key `lapwise-theme` |
| Saved laptops | `localStorage` key `lapwise-shortlist` |
| Chat sessions, messages, recommendation data, and debug data | `localStorage` key `lapwise-chat-sessions` |
| Comparison selection | In-memory React state, cleared on refresh |
| Explore filters and chat filters | Component state, not persisted |
| API query cache | In-memory React Query cache; data become stale after 30 seconds |

Saved chat history is interface history. A new request sends only its current query and filters; previous chat messages are not included in the API request (the backend tracks conversation context server-side via `conversation_id`).

## Limitations

- Mock mode's data set has 18 hard-coded laptop records, not the production catalog (the real backend serves the full dataset).
- Mock mode's recommendation engine is heuristic and deterministic, not AI/LLM-powered; similar-laptop results in mock mode are based on overlapping categories, not semantic similarity; its evidence and debug metadata are simulated.
- The Explore page's real API call sends `search` and filter params, but some visual filter selections (use case, CPU brand, display size) are only applied client-side in mock mode — the real backend infers those from free text instead.
- There is no authentication, pagination beyond `limit`/`offset`, request cancellation, or runtime response-schema validation for backend calls.
